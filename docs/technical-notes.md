# 朝花惜食（ZHAOHUAXISHI）

临期食品盲盒交易项目：Vue 3 + Vite 前端 + Java（Spring Boot 3）后端，包含**顾客端 / 商家端 / 平台管理端**三套界面与完整业务流程（选址 → 发布批次 → 下单支付 → 到店核销 → 退款 / 售后）。

数据落地在服务端数据库，多设备、多浏览器共享同一份业务数据；登录、订单、库存、积分、支付回调、超时任务全部由服务端负责。

## AI 助手接入

新增三端 Spring AI + MCP 智能查询，运行配置与查看入口见 [AI 接入说明](../ai-services/README.md)。只运行下面的前后端命令时，AI 会提示服务未连接；需要另外启动两个 Java 服务。

## 快速开始

```bash
npm install        # 安装前端依赖
npm run server     # 启动 Java 后端 API，默认 http://localhost:8787（首次启动初始化所选数据库并写入初始数据）
npm run dev        # 另开一个终端启动前端，http://localhost:5173（/api 已代理到 8787）
npm run build      # 前端生产构建，输出到 dist/
```

> 后端为 Spring Boot 3 + Java 17，需要 JDK 17 与 Maven。数据库默认使用 H2 文件库，配置 `ZHX_DB_URL`、`ZHX_DB_USER` 和 `ZHX_DB_PASSWORD` 后可直连 MySQL。显式配置 MySQL 后连接失败会停止启动，不会自动切换数据库。

默认 H2 数据库文件位于启动工作目录下的 `data/zhx-java.mv.db`（已加入 .gitignore）。需要重置 H2 时请先停止后端并备份数据库文件；切勿为了修复启动问题直接删除数据目录。

### 环境变量

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `ZHX_DB_URL` | `jdbc:h2:file:./data/zhx-java;...` | 默认 H2 文件库；可显式指定 MySQL，连接失败会报错 |

| `ZHX_AI_BASE` | `https://api.deepseek.com` | 兼容 OpenAI Chat Completions 的网关地址 |
| `ZHX_AI_MODEL` | `deepseek-chat` | 模型名 |

AI 助手现通过独立 Spring AI + MCP 服务查询业务数据；未启动 Java 服务或未配置模型密钥时，页面显示连接状态，不返回本地规则答案。详见 [AI 接入说明](../ai-services/README.md)。

## 架构与安全边界

前端只保存一个登录令牌（`localStorage` 的 `zhx_token`），业务数据一律通过 `/api` 读取，服务端按角色裁剪下发的数据范围。

| 领域 | 服务端实现 |
| --- | --- |
| 密码 | scrypt 加盐哈希（`scrypt$N$r$p$salt$hash`），源码与数据库中都没有明文密码 |
| 会话与鉴权 | HMAC-SHA256 签名令牌（含过期时间）；令牌只承载账号 ID，**角色与账号状态每次请求都从数据库读取**，伪造/篡改令牌无效，被停用账号立即失去所有接口访问权 |
| 接口权限 | 每个路由显式校验角色（顾客/商家/管理员），顾客令牌调用管理接口返回 403 |
| 订单归属 | 下单、支付、退款、售后、核销都在 SQL 条件中带 `user_id`/`store_id`，跨账号访问一律拒绝 |
| 数据共享 | 全部业务数据存储在所选 H2 / MySQL 数据库，换设备、换浏览器看到同一份数据，清浏览器缓存不丢单 |
| 并发与事务 | 交易写操作使用 Spring 事务；订单行锁协调支付、取消、核销和退款，扣库存用条件更新 `total - sold - reserved >= 1`，避免超卖 |
| 支付 | 两段式：`POST /api/orders/:id/pay` 只创建支付单（幂等），订单仍是「待支付」；服务端后台任务模拟渠道回调，回调确认后才把预留转成交、生成取货码、发放积分 |
| 超时任务 | Spring `@Scheduled` 每秒扫描：支付超时自动关单并释放预留、取货超时置为「超时未取」。与浏览器是否打开无关，也不依赖用户本机时间 |
| AI 密钥 | 浏览器只调 `POST /api/ai/chat`，Java 业务后端校验身份后转发独立 Spring AI 服务，密钥仅在 Java 服务环境变量中 |

支付渠道为**模拟实现**：`app.demo-delay.pay-ms` / `app.demo-delay.refund-ms` 控制回调延迟（默认支付 6 秒、退款 10 秒）。真实上线需替换为渠道下单接口 + 回调验签 + 退款对账。

## 关键业务规则

- 数据库金额使用 DECIMAL，以「元」存储；业务计算和前端接口以「分」表示，通过 Money 统一换算，避免浮点误差。
- 库存守恒：`总量 = 已售 + 预留 + 可售`，下单预留、支付成交、取消/退款按规则回补，均由服务端事务保证。
- 支付截止 = 下单后 3 分钟与批次取货截止的较早值，超时由服务端任务关单并释放预留。
- 普通退款：已付款且未领取、付款后不超过 15 分钟，并且当前时间严格早于取货截止前 2 小时；条件须同时满足，同一订单只受理一笔退款。
- 特殊售后：同一订单只允许一个处理中申请，商家同意后只生成一笔退款。
- 核销：同一取货码只能成功核销一次，重复扫码返回「重复核销」。
- 订单、支付、取货凭证、售后均校验订单归属，切换账号后无法访问他人订单。
- 积分在支付回调成交时按实付金额发放，退款到账时按订单记录回滚。

## 平台经营管控

管理员侧栏新增「门店管理」与「盲盒监管」。门店可按名称、地址、经营状态筛选，暂停和恢复均须填写原因；批次可按门店、批次号、状态筛选并强制下架。每次处置均通知商家，操作审计记录管理员身份、对象、原因及时间。

暂停门店会阻止新下单、发布批次、追加库存，并从附近门店和 AI 推荐中排除。已经创建的订单仍可按原规则支付、核销、退款和处理售后。恢复门店只恢复未过期且未停售批次的售卖资格，已停售/平台下架的批次不会自动恢复。平台下架不改库存、不删除订单、不自动退款；食品安全等无法履约情况仍需单独处理订单与售后。

首次启动会为已有数据库补充经营状态、原因和时间字段，保留原有账号及交易数据，无需重置数据库。管理员管控与账号停用是独立操作：暂停门店后，商家仍可登录履约；账号停用会禁止登录和接口访问，不应替代常规门店停业处置。


## 每日定时发布与首页折叠

正常启动后端时，会立即检查一次当天计划，此后每分钟检查一次。计划逻辑在 `com.zhx.task` / `DailyBatchService`，按北京时间执行。每家已配置门店每天最多自动发布一批，6—12份、固定价格，取货起点即发布时间；不提前发布未来日期，不制造销量。暂停经营或商家账号停用时不发布。启动时只补发当天仍在取货窗口内的批次，已截止则跳过。售罄、停售或平台下架后不重复生成；历史订单不变。后端关闭期间任务不会运行。

首页保留服务范围内符合搜索/分类条件的正常经营门店，有可购批次的门店优先，其余按距离排列。无货卡片分别提示预计上架（以实际发布为准）、已售罄、今日结束或暂无在售。首页每分钟刷新业务快照。每家卡片默认只显示按取货截止排序的前两个可购批次，第三个起折叠在「更多盲盒⌄」内，展开后显示「收起盲盒⌃」，不显示剩余数量，操作不跳转门店。商家仍可正常手动发布。
